# 02. 드라이버 (명령 문법 · 토글 · 파이프라인)

> 고정하는 계약: 내부 엔진의 진입점. 명령 문법, 레벨 on/off 토글, 파이프라인 실행 순서. — §9 척추 ② '드라이버+토글'.

드라이버는 argv(문서 01에서 받은)를 파싱해 **파이프라인을 조립·실행**한다. 명령 계약의 단일 진실 원천.

## 명령 문법

```
blackshell <command> [args] [options]
```

git을 본뜬 **2단계 모델**이다 — 봉인할 유닛을 `add`로 **스테이징**한 뒤, `enshell`이 스테이징된 집합을 실제로 봉인한다(`git commit` 자리). 구간별로 레벨을 달리 조합하려면 "무엇을 봉인할지"를 "봉인 실행"과 분리하는 게 자연스럽다.

| 명령 | 역할 | git 대응 |
| --- | --- | --- |
| `add <ir-file>` | 봉인 유닛을 **스테이징**에 올림 (유닛별 `--level` 지정 가능) | `git add` |
| `drop <ir-file>` | 스테이징에서 **내림** | `git restore --staged` |
| `list` | 지금 스테이징된 유닛·레벨 목록 | `git status` (staged 부분) |
| `enshell` | 스테이징된 **모든 유닛**을 봉인 → 아티팩트 출력 (게이트 → 노이징) | `git commit` |
| `check <ir-file>` | 게이트만 (§5 조건1 판정) — `add` 전 미리보기 | — |
| `run <ir-file> [--input ...]` | IR를 인터프리터로 실행 (문서 03) — **PoC/dev 전용, 프로덕션 대응물 없음** | 디버깅·하네스용 |
| `help [command]` | 사용법 | — |

- `enshell`은 **인자 없이** 스테이징 집합에 작용한다(`git commit`처럼). 유닛마다 `add` 때 지정한 레벨로 봉인.
- `check`는 스테이징과 무관하게 파일 하나를 바로 판정 — 올릴 가치가 있는지 미리 보는 용도.
- `run`은 등가 하네스(문서 05)가 올라서는 **원시 연산**이자 수동 디버깅 도구다. 제품 명령(`add`/`drop`/`list`/`enshell`/`check`)과 달리 **PoC/dev 전용**이며, 프로덕션에선 실행이 네이티브로 넘어가 대응물이 없다(하네스로 흡수). shipped CLI에선 숨기거나 `--dev` 뒤로 둘 수 있다.

> PoC에서 유닛은 **IR 파일**(문서 03의 JSON)로 받는다. 프로덕션에서는 `add <source.c>`로 소스를 받아 Clang 프런트엔드가 IR를 만든다 — **명령 문법은 동일**, 앞단에 프런트엔드만 끼워진다.

### 스테이징 상태 (인덱스)

- `add`/`drop`/`list`가 공유하는 스테이징 상태는 **작업 디렉터리의 인덱스 파일**에 둔다 (PoC: `.blackshell/stage.json` 류). git의 `.git/index`에 대응.
- 유닛 경로 + 유닛별 선택 레벨을 기록. `enshell`은 이 인덱스를 읽어 파이프라인을 유닛 수만큼 돌린다.
- 스테이징 모델은 파이프라인 **위에 얹힌 CLI UX 층**이다 — 게이트·노이징·검증(문서 04·05)은 유닛 하나 단위로 그대로 돌아가고, `add`/`drop`은 그 입력 목록을 관리할 뿐.

## 레벨 토글

§6의 봉인 강도 레벨(L0~L3)을 **독립적으로 on/off.** 구간별 조합이 목적이라 레벨은 **유닛별로 `add` 때 지정**하고 인덱스에 저장된다.

| 옵션 | 붙는 명령 | 의미 |
| --- | --- | --- |
| `--level L1,L2,L3` | `add` | 그 유닛에 적용할 노이징 레벨 선택 (기본: 없음 = L0 항등) |
| `--no-gate` | `enshell` | 게이트 건너뜀 — **디버깅 전용, 위험** (아래 주의) |
| `--emit-ir <path>` | `enshell` | 변환 결과 IR 덤프 (하네스·검사용) |
| `--verify` | `enshell` | 봉인 중 등가 하네스(문서 05)를 매 패스 돌림 |

레벨 선택은 **패스 레지스트리**(문서 04)에서 해당 레벨의 패스들을 순서대로 뽑아 파이프라인에 넣는 것으로 구현된다. 유닛마다 인덱스에 기록된 레벨대로 서로 다른 조합이 적용된다.

## 파이프라인 실행 순서 (고정)

`enshell`은 인덱스의 **스테이징된 유닛마다** 아래를 반복한다:

```
for 유닛 in 스테이징:
   IR 로드/빌드
   → 게이트 (IR→통과|거부)        ── 거부면 exit 2, 여기서 중단
   → 노이징 L1 → L2 → L3          ── 유닛의 --level로 선택된 것만, 순서 고정
   → (--verify면 매 패스 뒤 등가검증)
   → 결과 IR 출력 (아티팩트)
```

**순서 불변식** (plan §6):
- **게이트는 노이징 "앞"**의 go/no-go. 거부 시 즉시 중단(exit 2), 노이징 진입 금지.
- **노이징은 L1→L2→L3 순**. (프로덕션에선 LLVM 최적화기 "뒤"에 꽂힘 — 안 그러면 사용자 최적화기가 노이징을 되돌림.)
- 각 단계는 **같은 IR 계약**(문서 03)을 입출력하므로 더미↔실제 무중단 교체 가능.

## PoC → 프로덕션

- **바뀌는 것:** 파싱 구현 언어(Python → C++ 바이너리로 흡수), IR 빌드 앞단(소스 → Clang 프런트엔드).
- **안 바뀌는 것:** 명령 문법, 토글 의미, 파이프라인 순서/불변식. → 전환 시 "계약"은 보존, 재작성은 패스 몸통뿐(§9).

## 출하 전 체크

- [ ] `--no-gate`는 개발 빌드에서만. 릴리스 빌드에선 비활성 또는 큰 경고.
- [ ] 게이트 거부가 exit 2로 정확히 전파되는가 (문서 01).
- [ ] `--level` 없이 `add`한 유닛은 L0(항등)로 "정확하지만 보호 안 됨" 상태인가.
- [ ] `enshell` 후 스테이징이 어떻게 되는가(비움 vs 유지) 동작이 정의·문서화되어 있는가.
