# 05. 등가검증 하네스

> 고정하는 계약: 변환 전후 IR이 같은 입력에 같은 출력을 내는지 검증. — §9 척추 ③. 전체 파이프라인을 가로지르는 **안전망**. 더미 단계부터 상시 켜 둔다.

plan §6 "모든 변환은 빌드마다 L0과 같은 입력에 같은 출력을 내는지 자동 비교한다. 깨지면 변환 패스가 잘못된 것"의 집행 장치.

## 시그니처

```
verify(baseline: IR, candidate: IR, inputs: [InputVector]) -> Report
# Report = { equivalent: bool, mismatches: [ {input, expected, actual} ] }
```

- `baseline` = L0(원본 IR), `candidate` = 변환된 IR.
- 각 입력 벡터를 **둘 다 인터프리터(문서 03)로 실행**해 `returns` 출력을 비교.
- 하나라도 다르면 `equivalent:false` + 어긋난 지점들.

## 비교 기준 — "같다"의 정의

- **관측 가능한 출력만** 비교한다 = `returns` 값. (내부 레지스터·명령 수·실행 경로는 비교 안 함 — 노이징은 바로 그걸 바꾸는 게 목적이므로.)
- 이는 §4 "f는 경계에 산다"와 정렬: 보존해야 하는 건 경계의 입출력 매핑뿐.

## 입력 벡터 공급

| 방식 | 용도 |
| --- | --- |
| 명시 벡터 (고정 테스트셋) | 회귀 테스트, 결정적 CI |
| 생성기 (랜덤/경계값) | 넓은 커버리지 |

> PoC는 명시 벡터로 충분. 입력 공간이 커서 전수는 불가하므로(§5 조건2) **표본 검증**이다 — "증명"이 아니라 "회귀 안전망". 반례를 못 찾은 것이지 등가 증명은 아니라는 점을 리포트에 명시.

## 언제 돌리나

- **매 패스 뒤** (드라이버 `--verify`, 문서 02): L1 적용 후 vs L0, L2 후 vs L0 … 누적 변환이 여전히 L0과 등가인지.
- **CI 게이트**: 실제 패스로 교체할 때마다 하네스 통과가 머지 조건. 이게 "더미→실제 무중단 교체"를 실제로 지켜주는 장치.

## 위치 — 언어/배포

- 하네스는 **dev/CI 도구**(Python). shipped npm 경로에 안 실림(메모리 `language-layering`).
- 인터프리터는 PoC에선 하네스와 같은 Python 런타임. 프로덕션에선 네이티브 실행 결과(또는 LLVM JIT)를 비교 대상으로.

## PoC → 프로덕션

- **바뀌는 것:** 실행 백엔드(토이 인터프리터 → 네이티브/JIT 실행), IR 타입.
- **안 바뀌는 것:** `verify()` 시그니처, "관측 출력만 비교" 기준, 매-패스·CI 게이트 운용. → §9 "등가 검증 하네스는 그대로 넘어간다".
